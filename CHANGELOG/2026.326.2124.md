# 2026.326.2124 — fix(ci): derive the packaged release from charly's releases, and never lag it again

## Summary

Fixes opencharly/layer-charly#23 at its root: this repo's published packages had not been rebuilt since 2026-10-06, so every image that installed `charly` from here got packages built by an sdk that still declared the variant family's mutual `Replaces`. `pacman -Syu` on the next layer then resolved BOTH `charly-full` and `charly-minimal` and refused the transaction:

```
:: charly-full-2026.279.2144-1 and charly-minimal-2026.279.2144-1 are in conflict
error: unresolvable package conflicts detected
```

sdk#397 (2026-10-14) removed those `Replaces` — the toolchain has been correct for six weeks. What kept the failure alive is that packaging was a hand-typed `workflow_dispatch`: nothing tied this repo to the releases it packages.

- **The version is derived, not typed.** Empty `version` = the newest charly release (`gh release list`); empty `charly_lib_version` = the newest charly-lib release. The inputs remain for a deliberate backfill.
- **A daily `schedule` runs the same job**, so a new charly release is packaged without anyone remembering.
- **A `resolve` job skips when the SERVED database already carries the version** (`charly-<version>-1` in `charly.db.tar.zst`), so the schedule is idempotent and a run that crashed after publishing converges instead of republishing.

## How tested

The skip test reads exactly what the site serves, and both cases are executed rather than asserted:

```
$ DB=$(curl -fsSL https://opencharly.github.io/charly-arch/amd64/charly.db.tar.zst | zstd -dc | tar -t)
$ echo "$DB" | grep -qx "charly-2026.279.2144-1/" ; echo "skip=$?"
skip=0 (0 = already published -> the schedule skips)
$ echo "$DB" | grep -qx "charly-2026.326.1922-1/" ; echo "skip=$?"
skip=1 (1 = not published -> the schedule builds)
```

So the daily schedule skips the stale release (it is already published) and builds the current one (`v2026.326.1922` is not in the DB). The earlier draft of this branch compared against `charly-<version>-1` without the trailing slash the database actually lists, which could never match — corrected here, and the same run shows it.

The dispatch inputs are honoured: `resolve` reads `inputs.version` / `inputs.charly_lib_version` (not its own outputs), so a deliberate backfill still packages the version it names; empty means "the newest release". The workflow file parses (`yaml.safe_load`).

The end-to-end proof is the first run of the changed workflow: dispatched for `v2026.326.1922`, it must publish packages built by the sdk that carries opencharly/sdk#397's no-`Replaces` metadata. That run and its outcome are reported on opencharly/layer-charly#23 before that issue closes.
